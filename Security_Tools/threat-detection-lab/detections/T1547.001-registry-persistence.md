## What the Attack Did
Added an entry to the Windows registry Run key pointing to a
malicious executable path. The Run key causes the specified
program to execute automatically every time the user logs on,
giving an attacker persistent access that survives reboots
without requiring elevated privileges or a service installation.

## False Positive Considerations
- Legitimate software commonly writes to Run keys during installation
  (browsers, cloud sync clients, messaging apps)
- Key differentiators: unexpected binary path (temp/appdata),
  randomized key name, binary with no digital signature
- The Sysmon ruleName field T1060/RunKey is a strong signal —
  Sysmon itself flagged it as a known persistence technique

## Triage Steps
1. Note the full registry path and the binary it points to
2. Verify whether the binary at that path exists and is signed
3. Check the binary hash against threat intelligence
4. Review when the key was created and by what process
5. If malicious — delete the registry key and quarantine the binary

## Escalation Decision
**Escalate: Yes if** — binary path is in a user-writable
directory, binary is unsigned, or key name is randomized.
Combined with other indicators like LSASS dumping this
becomes a Critical incident.

## Analyst Notes
Notable: the data.win.eventdata.ruleName field shows
"T1060, RunKey" — Sysmon's SwiftOnSecurity config
automatically tagged this as a known persistence technique.
This demonstrates the value of a well-configured Sysmon
deployment over default Windows logging.
